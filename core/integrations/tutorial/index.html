    构建你的第一个集成

    逐步构建一个小而完整的集成，从脚手架（scaffold）到配置流程（config flow）、协调器（coordinator）、传感器、测试，以及一个达到 Bronze 级别的拉取请求（pull request）。

    在本教程中，你将为本地网络上的一台空气质量监测仪构建一个完整的集成。它通过 UI 进行设置，每分钟轮询一次监测仪，并将其温度、湿度和细尘显示为传感器。在这个过程中，你会接触到 core 中新集成所需的每一个部分：一个库、一个配置流程（config flow）、一个协调器（coordinator）、实体、测试、文档、一个品牌标识，以及一个拉取请求。

    到最后，你的集成将满足质量分级（quality scale）中 Bronze 级别的每一条规则，这是 core 中新集成的最低要求。每一步都会说明它照顾到了哪些规则，最后几步则把它们全部核对一遍。

    监测仪及其库 exampleair 是为本教程虚构的。你可以用自己的设备和它的库跟着做：代码的形状是一样的，只是名称和数据不同。这些代码以 theben_conexa 为蓝本，它是一个最近加入 core 的小型 Bronze 集成，面向本地设备，包含一个传感器平台、一个协调器以及同样的一组测试。如果有帮助，你可以在阅读本页时同时打开它的代码。

    对配置条目（config entry）、平台（platform）或协调器这些词感到陌生？请先阅读集成是如何融入的。这只需要五分钟。

    开始之前

    • **一个开发环境。**按照你的第一次贡献或开发环境指南搭建一个。请在该环境中、从你 core 检出（checkout）的根目录运行本页上的每一条命令。
    • **一个适合进入 core 的设备或服务。**它必须是人们今天就能购买和使用的，并且有真实的用户群。参见创建集成。对于新集成，项目建议你先在 Marketplace 中发布。自定义集成（custom integration）的构建方式相同，因此你在这里学到的所有内容都可以迁移过去。
    • **一些 Python 基础。**你应该熟悉类、async 和 await 以及类型提示（type hints）。你还不需要了解 Home Assistant 的代码。
    • **时间。**规划几个晚上。之后的审查比编写代码花的时间更长，通常需要数周。这是正常的。

    然后为你的集成创建一个分支，从 Home Assistant 最新的 dev 分支开始。请先做这件事：core 的 pre-commit 钩子包含 no-commit-to-branch，它会拒绝在 dev、rc 和 master 上的每一次提交。

    upstream 是你在你的第一次贡献中添加的 home-assistant/core 远程仓库。

    1. 从库开始

    你的集成从不直接与设备通信。这项工作由 PyPI 上的一个 Python 库完成，你的集成只在库和 Home Assistant 之间进行转换。如果你的设备还没有库，请先编写一个：构建 Python 库解释了怎么做，以及在 core 接受它之前它必须满足什么条件。

    • 它是异步的，因此永远不会阻塞事件循环（event loop）。
    • 它接受调用者传入的 aiohttp 会话，因此可以使用 Home Assistant 的共享会话。
    • 它抛出自己的异常，因此集成能够区分设备无法访问和其他问题。

    Core 对库的发布方式也有要求。这就是依赖透明（dependency-transparency）规则：

    • 源代码位于公开的仓库中，采用 OSI 认可的许可证，如 MIT 或 Apache 2.0。
    • 每个版本都发布在 PyPI 上，由公开的 CI 流水线构建和发布，而不是手动上传。
    • PyPI 上的每个版本都对应该仓库中的一个带标签的版本（tagged release）。

    在开始集成之前先设置好这些。你需要在拉取请求中链接发布工作流（release workflow）和标签，审查者会检查它们。

    3. 检查清单文件

    打开 manifest.json。脚手架根据你的回答填写了它，并添加了几个空键（用于依赖和发现）。删除这些空键：core 中几乎所有集成都会省略它们。剩下的是：

    • quality_scale 从一开始就是 bronze：新集成必须至少达到 Bronze。在 quality_scale.yaml 中的每条 Bronze 规则都变为 done 或 exempt 之前，hassfest 会为此报告错误。你会在第 11 步达到这一点。
    • requirements 使用 == 将你的库固定到确切版本。Hassfest 要求这样做，而且这也是依赖透明的另一半。

    5. 使用协调器获取数据

    监测仪在一个请求中返回其所有数值。协调器每分钟发出一次该请求，并将结果交给所有实体。当监测仪停止响应时，它还会将实体标记为不可用，并且只记录一次日志。

    创建 coordinator.py：

    • ExampleAirConfigEntry 是一个带类型的配置条目。它的 runtime_data 就是协调器，因此你的平台可以免费获得一个带类型的协调器。
    • update_interval 由集成固定。用户无法更改它，配置流程也绝不能询问它。选择一个适合数据的间隔：参见适当轮询（appropriate-polling）。
    • UpdateFailed 告诉协调器更新失败。它的消息是可翻译的，来自 strings.json 的 exceptions 部分。
    • 协调器位于 coordinator.py 中，基础实体位于 entity.py 中。这就是通用模块（common-modules）规则。

    6. 设置配置条目

    __init__.py 将一切连接起来。Home Assistant 会为每个配置条目调用 async_setup_entry：在启动时，以及在用户添加监测仪时。将该文件替换为：

    • async_config_entry_first_refresh 在任何实体存在之前获取第一批数据。当监测仪离线时，它会引发 ConfigEntryNotReady，Home Assistant 会在稍后重试设置。这就是先测试后设置（test-before-setup）规则。
    • 协调器放在 entry.runtime_data 中，而不是 hass.data。这就是运行时数据（runtime-data）规则。
    • _PLATFORMS 只有一个平台。新集成从一个平台开始：更多平台会在后续的拉取请求中添加。
    • async_unload_entry 让用户无需重启即可移除或重新加载集成。
    • 没有 async_setup，因为这个集成没有添加自己的动作（action）。如果你的集成有，请在 async_setup 中注册它们，而不是在这里。这就是动作设置（action-setup）规则，对于本集成它是豁免的。

    7. 添加实体

    首先，在 entity.py 中创建一个基础实体。监测仪的每个实体共享相同的设备和相同的协调器：

    • CoordinatorEntity 将实体订阅到协调器，并在更新失败时使其不可用。
    • _attr_has_entity_name = True 让每个实体在其设备的上下文中命名，比如“客厅温度”。这就是实体名称（has-entity-name）规则。
    • DeviceInfo 将监测仪放入设备注册表（device registry），这样用户看到一个包含其所有传感器的设备。
    • 这些实体自身不订阅任何内容。CoordinatorEntity 在 async_added_to_hass 中订阅协调器，并在实体被移除时取消订阅。如果你以后添加自己的订阅，比如库推送的更新，请遵循实体事件设置（entity-event-setup）规则。对于本集成，该规则是豁免的。

    然后是传感器平台，位于 sensor.py 中：

    • 实体描述（entity description）将每个传感器描述为数据：它的设备类别（device class）、单位，以及如何获取其数值。以后添加一个传感器只是在 SENSORS 中多一个条目。
    • 设备类别为每个传感器提供名称、图标和正确的单位换算。因为这些传感器有设备类别，所以它们不需要自己的名称。
    • 唯一 ID 由序列号和键组合而成。它永远不会改变，并且正是它让用户能够重命名实体。这就是实体唯一 ID（entity-unique-id）规则。

    实体与平台为每种实体类型都有一页，比如传感器实体。

    10. 添加品牌标识和文档

    品牌标识

    你集成的图标和标志（logo）放入 brands 仓库中，放在以你的域命名的文件夹里：core_integrations/example_air/。至少添加 icon.png 和 icon@2x.png，如果品牌有宽版标志，还要添加 logo。品牌与品牌图像列出了每个文件和图像要求。这就是品牌（brands）规则。

    文档

    对于 Bronze，页面需要三样东西，每一项都是一条独立的规则：

    • 产品描述，放在开头几行，并附上制造商的链接。这就是 docs-high-level-description 规则。
    • 安装步骤，把用户在开始之前必须做的任何事情作为前置条件列出。这就是 docs-installation-instructions 规则。
    • 如何移除集成，包括在 Home Assistant 之外遗留的任何内容。这就是 docs-removal-instructions 规则。

    12. 发起拉取请求

    打算先在 Marketplace 发布？请改为按照发布自定义集成操作，等你的集成成熟并拥有用户群后再回到这一步。

    在推送之前，对所有内容运行 linter，并最后一次运行 hassfest，不跳过任何内容。包含它们更改的每一个文件，也包括你的集成文件夹之外的文件：

    现在你的拉取请求包含你的集成、它的测试、生成的文件以及更新后的依赖文件。在你开始时创建的分支上提交，推送到你的 fork，然后针对 home-assistant/core 的 dev 分支发起拉取请求。提交拉取请求会逐一讲解模板。对于一个新集成：

    • 选择 New integration 作为变更类型。
    • 解释这个设备或服务是什么，并链接到你库的源代码仓库、它的发布工作流，以及你所依赖版本的标签。
    • 链接文档和品牌的拉取请求。
    • 保持只包含你在这里构建的内容：一个平台，没有更多。诊断、动作、重新认证和选项以后再说，每次一个拉取请求。

    然后等待就开始了。新集成的审查需要时间，有时需要数周。在等待期间，审查其他人的拉取请求：这是学习的最佳方式，也能让整个队列为每个人更快地推进。发起拉取请求之后解释了接下来会发生什么。

    接下来做什么

    你的集成已经合入。现在让它变得更好，每次一个小的拉取请求：

    • 提升级别（raise tier）到 Silver：优雅地处理离线设备，如果你的设备需要凭据则添加重新认证，并达到超过 95% 的测试覆盖率。
    • 添加诊断（diagnostics），让用户在报告错误时可以分享集成所看到的内容。
    • 支持发现（discovery），让 Home Assistant 自动找到监测仪。
    • 添加第二个平台，比如用于空气质量报警的二进制传感器（binary sensor）。
